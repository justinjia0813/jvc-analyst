# 投资论点

回答“这个项目为什么可能是好投资、为什么可能不是、哪几件事一旦查清就能定性”。默认交付 `04-thesis-test.md`。

## 适用级别

最低适用级别：**L1+**（有初筛或一次访谈就能跑；材料越多越扎实）。

## 三种写法

| 写法 | 什么时候用 | 默认文件 |
| --- | --- | --- |
| **双向**（默认） | 想要一份完整的正反判断 | `04-thesis-test.md` |
| **正方** | 准备向合伙人讲这个项目为什么值得看 | `04-bull-case.md` |
| **反方** | 想让人专门挑刺、模拟投决会上最难的问题 | `04-bear-case.md` |

正方和反方只改变篇幅重心：正方稿也要保留最致命的一条反驳，反方稿也要承认最强的一条支持。

## 执行

1. 读已有材料：初筛、纪要、商业经济、赛道研究、工作簿，有什么用什么。
2. 把投资逻辑拆成 3–5 条论点，每条是一句能被证明或推翻的话（“客户会从一次性买设备转向按年付服务费”，而不是“商业模式好”）。
3. 每条论点写：最强支持、最强反驳或替代解释、什么情况下论点就错了（可观察的信号）、最快的验证动作。
4. 反方视角可以借投决会上不同角色来想：做过这个行业的合伙人、只看数字的风控、竞争对手的投资人。不要求凑满角色。
5. 写一段总判断：哪几条论点目前站得住、哪几条是整个项目的命门。

## 输出结构

```
# {公司}：投资论点｜{日期}｜{双向/正方/反方}

## 总判断（3–5 句：最站得住的逻辑、最致命的风险、决定成败的一两件事）

## 论点
### 论点 1：{一句话}
- 支持：……
- 反驳：……
- 什么情况下就错了：……
- 最快怎么验证：……

## 命门：一旦查清就能定性的 1–2 件事

## 依据（来源清单，附录）
```

## 文件位置

用户指定路径优先；否则写进材料所在的项目或赛道文件夹根目录（不放进原始材料子目录）；都没有时问一次放哪。中间文件（JSON、转出的文本、计算脚本、证据台账）放在同目录的 `_work/`。同名文件已存在时不覆盖，加日期后缀。

## 反合理化约束

- 正方不删风险，反方不把“缺证据”写成“已经失败”。
- 公司自述照样可以用来支持论点，但要标 `[创始人自述]`；整条论点只靠公司自述时，在“什么情况下就错了”里写明要验证什么。
- 供应商的客户、产能或门槛不能直接搬到目标公司身上。
- 不写投/不投的结论；总判断写“站得住的是什么、命门是什么”。
- 证据内核默认不启用；用户要求 `--rigor` 时按 [调用合同](../jvc-research-core/references/caller-contract.md) 以 `jvc-thesis-test` 身份审查（历史上的 `04-bull-case.md`、`04-bear-case.md` 台账可继续用 `jvc-bull-case`、`jvc-bear-case` 身份复审）。

## 完成

合伙人读完总判断，就知道这个项目的投资逻辑是什么、最可能死在哪、下一步查哪一件事最值。
